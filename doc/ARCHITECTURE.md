# Pitchoune Timer — Software Architecture

A timer for children (up to 11 years old). Each child has a **time bank**: an
adult deposits or removes minutes, and the child **withdraws** the amount of
their choice, at most what is left, which is then spent as an animated
countdown. When a countdown ends, the app comes to the foreground and offers to
withdraw a little more, then hands the screen back to the app the child was
using. When the bank is empty, the child stays on Pitchoune Timer: the end
screen holds them until they stop, and in child mode the app keeps them on
their timer.

The time banks are shared by all the family's devices through Cloud Firestore.

## 2. Overview

### 2.1 Layers

```
┌───────────────────────────────────────────────────────────────────┐
│ SCREENS (lib/*_screen.dart)                                       │
│   FamilyScreen        HomeScreen ──push──▶ TimerScreen            │
└──────┬───────────────────────┬───────────────────────┬────────────┘
       │ use                   │ call                  │ call
       ▼                       ▼                       ▼
┌──────────────────┐  ┌───────────────────────┐  ┌──────────────────────────┐
│ EFFECTS          │  │ FAMILY (family.dart)  │  │ MODEL (child.dart)       │
│ (effects.dart)   │  │ FamilyService         │  │ ChildrenStore            │
│ PitchouneTitle   │  │  anonymous sign-in,   │  │  (ChangeNotifier)        │
│ BubbleBackground │  │  family code,         │  │  ├─ List<Child>          │
│ ConfettiBurst    │  │  create/join/leave    │  │  └─ TimerSession? (local)│
│ RoundButton      │  └──────────┬────────────┘  └───────────┬──────────────┘
│ ChildAvatar      │             │                           │ ChildrenBackend
└──────────────────┘             │                           │ (backend.dart)
                                 ▼                           ▼
                      ┌─────────────────────────────────────────────────┐
                      │ Firebase: Authentication (anonymous)            │
                      │           Cloud Firestore (+ local cache)       │
                      └─────────────────────────────────────────────────┘

TimerScreen ──▶ Alarm (alarm.dart)        ══pitchoune/alarm══▶  MainActivity.kt
            │                                                    Alarm.kt ──▶ AlarmManager
            ├─▶ Screen (screen.dart)      ══pitchoune/screen══▶ MainActivity.kt
            │                                                    FLAG_KEEP_SCREEN_ON, moveTaskToBack,
            │                                                    Guard.kt,
            │                                                    CountdownNotification.kt (+ Ticker),
            │                                                    ChildModeService.kt, HomeActivity.kt
            └─▶ Apps (apps.dart)          ══pitchoune/screen══▶ Apps.kt (child mode app list)
```

Four principles drive this split:

- **Screens store nothing durable.** Any data that must survive goes through
  `ChildrenStore` (shared data) or `FamilyService` (this device's family).
- **The store knows nothing about the UI.** It notifies its listeners
  (`notifyListeners`), and the UI rebuilds itself. This is the *Observer*
  pattern, the equivalent of a Qt `dataChanged()` signal.
- **The store knows nothing about Firestore.** It talks to a `ChildrenBackend`
  interface: Firestore in the app, memory in the tests.
- **Native code is isolated behind facades** (`Alarm`, `Screen`). On a platform
  other than Android, they do nothing, so the rest of the app ignores that
  Kotlin exists.

### 2.2 Application lifecycle

0. `main()` first shows `_StartupScreen` (a spinner). Android keeps its launch
   screen (the icon) until Flutter draws a first frame, so anything awaited
   before `runApp` that hangs would leave the icon on screen forever. If a
   startup step fails, the same screen shows the error ("Pitchoune Timer could
   not start"): readable on the device, without adb.
1. `main()` initialises Flutter, locks the orientation to portrait, initialises
   Firebase (at most 20 s), then lets `FamilyService` read this device's family
   code and sign in anonymously (at most 15 s: without network, the family
   screen offers to try again).
2. `main()` also loads `DeviceSettings`, the settings of this tablet account.
3. `PitchouneApp` shows `FamilyScreen` while the device has no family, and
   `_FamilyHome` otherwise. Since it listens to `FamilyService`, joining or
   leaving a family switches the screen by itself.
4. `_FamilyHome` creates the family's `ChildrenStore` and waits for the first
   list of children. Then, depending on the tablet's mode:
   - **parent mode**: `HomeScreen`, the list of every child;
   - **child mode**: directly the `TimerScreen` of the chosen child, as the
     root screen (`standalone`). There is no list of children.

   It listens to `DeviceSettings`: changing the mode in the settings swaps the
   root screen at once.
5. If a `TimerSession` is found at that point (the app was killed during a
   countdown), the countdown is resumed: in parent mode by pushing `TimerScreen`
   in *resume* mode, in child mode by the root `TimerScreen` itself.

## 3. Model, family and persistence

### 3.1 `Child` — `lib/child.dart`

| Field | Type | Role |
|---|---|---|
| `id` | `String` | Firestore document id |
| `name` | `String` | Shown everywhere |
| `avatar` | `String` | An animal emoji |
| `colorIndex` | `int` | **Index** into `childColors` (not the color itself) |
| `seconds` | `int` | Raw bank value; see `balance` |
| `createdAt` | `int` | Creation time in ms, for a stable display order |
| `runningUntil`, `runningOn` | `DateTime?`, `String?` | Set while a countdown runs, and on which device |

`Child` is **immutable**: every change goes through the backend, which sends
back a fresh list. Two computed properties:
- `balance` = `max(0, seconds)`. When two devices debit at the same time,
  `seconds` can briefly go below zero; the app never shows or uses a negative
  balance.
- `runningElsewhere(deviceId)`: a countdown for this child is running right now
  on another device. The home screen shows "In use until 18:42" and refuses to
  start a second countdown.

**Choice: the balance is stored in seconds**, even though adjustments are made
in minutes. The countdown spends time to the second: stopping a countdown at
4 min 37 must leave 4 min 37, not 4 or 5 minutes.

**Choice: store a color index.** The palette can change without migrating the
data, and the modulo (`index % childColors.length`) guards against an index that
has become too large.

### 3.2 `TimerSession` — `lib/child.dart`

It describes the countdown **running on this device**, that is, one withdrawal
from the bank: which child, the planned end time, the amount withdrawn
(`total`, used to draw the gauge), the bank balance when the countdown started
(`balanceAtStart`, to know whether it empties the bank) and the part already
debited (`debited`).

It is stored **locally** (SharedPreferences), not in Firestore: it is what this
device needs to resume a countdown if Android kills the process in the
background, which happens often to save battery.

### 3.3 `ChildrenStore` — `lib/child.dart`

The single source of truth for the screens. It extends `ChangeNotifier` and
listens to the backend:

```
user action ─▶ store.addMinutes(id, +1)
                 └─▶ backend.increment(id, +60)
                        └─▶ Firestore: applied to the local cache at once,
                            sent to the server when the network allows
                               └─▶ snapshot ─▶ store: new List<Child>
                                     └─▶ notifyListeners() ─▶ the screens rebuild
other device ─────────────────────────────▶ snapshot (same path)
```

- **Increments, never absolute values.** Every change to a bank is sent as
  `+60`, `−5`… (`FieldValue.increment` in Firestore). If a parent adds a minute
  on the phone while the tablet debits a countdown, both changes add up. With
  "write the new value", the last write would erase the other.
- **Writes are not awaited** by the UI: with Firestore, the future only completes
  once the server has confirmed, which may take a while (or until the network
  comes back). Errors are logged by `_guard`.
- **Bounds**: `addMinutes` computes the target value clamped to `[0, 24 h]`,
  then sends the difference.
- **Startup**: `load()` waits for the first list at most 5 seconds, so that the
  app also starts offline (Firestore then serves its local cache).

### 3.4 `ChildrenBackend` — `lib/backend.dart`

An interface (`watch`, `add`, `update`, `increment`, `remove`) with two
implementations:

| Implementation | Used by | Detail |
|---|---|---|
| `FirestoreBackend` | The app | `families/{familyId}/children/{childId}` documents |
| `MemoryBackend` | The tests | A `Map` and a synchronous stream; no network, no Firebase |

*C++ analogy:* an abstract class with pure virtual methods, injected into the
store's constructor. This is what makes `ChildrenStore` testable on a PC with
`flutter test`.

### 3.5 `FamilyService` — `lib/family.dart`

- **Anonymous sign-in.** Each device gets a permanent Firebase user id without
  any account or e-mail. It needs the network on the very first launch only.
- **Family code.** 12 characters from an alphabet without look-alikes (no `0`/`O`
  or `1`/`I`), drawn with `Random.secure()`, shown as `ABCD-EFGH-JKLM`. About
  10^18 possible codes: it cannot be guessed. The code **is** the Firestore
  document id of the family.
- **Create**: creates `families/{code}`, adds this device to `members`, and moves
  in the children saved locally by older versions of the app.
- **Join**: checks that the family exists, then adds this device to `members`.
- **Leave**: removes this device from `members`. The children stay in the family.
- The family code is remembered locally (SharedPreferences).
- **QR code.** The family sheet also shows the code as a QR code, whose text
  is `pitchoune-family:<code>` (`qrPayload`). `codeFromQr` accepts only that
  prefix followed by 12 characters of the alphabet, so any other QR code (a
  web link, a product label) is ignored. The QR code carries exactly the same
  secret as the typed code: it is a faster way to type it, not a new right.

### 3.6 Firestore data and security rules — `firestore.rules`

```
families/{familyCode}                    { createdAt }
families/{familyCode}/members/{uid}      { joinedAt }          one per device
families/{familyCode}/children/{childId} { name, avatar, colorIndex, seconds,
                                           createdAt, runningUntil, runningOn }
```

The security rules, pasted in the Firebase console, enforce the access model:

| Who | May |
|---|---|
| Any signed-in device | Read **one** family document by its code (to check it exists before joining), and create a family |
| Any signed-in device | Add or remove **itself** as a member of an existing family |
| A member | Read and change the family's children |
| Nobody | List the families (a code cannot be discovered by browsing) |

The rules also check the shape of a child (name of 1 to 20 characters, integer
seconds…).

### 3.7 `DeviceSettings` — `lib/settings.dart`

The settings of **this tablet account**, never shared with the family:

| Setting | Values |
|---|---|
| `mode` | `DeviceMode.parent` (default) or `DeviceMode.child` |
| `childId` | In child mode, the child this tablet account belongs to |

They are stored in SharedPreferences, which Android keeps **per user profile**
(see [§9.9](#99-where-an-apps-local-data-lives)). On a tablet with a parent
account and a child account, each account has its own mode: the parent account
in parent mode, the child account in child mode for that child. If the chosen
child is deleted from the family, the tablet falls back to the parent home
screen.

## 4. Screens

### 4.1 `HomeScreen` — `lib/home_screen.dart`

It is a `StatelessWidget`. It keeps no state of its own: it **listens** to the
store through `ListenableBuilder`.

| Sub-component | Role |
|---|---|
| `HomeScreen` | Gradient background + bubbles + `CustomScrollView` (title, family button, list or empty state) + floating button |
| `_showFamily()` | Bottom sheet "Add a device": the family QR code (`FamilyQrCode`), the code in text (copy button), and *Leave this family* |
| `ParentBanner` | Shown while parent mode is on: time left and a *Lock* button |
| `ChildCard` | One card per child. *Tap* = start the timer, *long press* = options menu. Shows "In use until …" when the child's timer runs on another device |
| `_EmptyState` | Shown when there are no children |
| `_ChildDialog` | Name entry and animal choice (used for both add and edit) |
| `askChildDetails()` | Opens `_ChildDialog` and returns a `(name, avatar)` *record*, or `null` |

**Notable points:**

- The list uses *slivers* (`CustomScrollView`, `SliverList.separated`), so the
  title scrolls with the list instead of staying fixed.
- Each card has a `ValueKey(c.id)`. If a child in the middle of the list is
  deleted, Flutter knows which card disappeared, and internal states (press
  animation) don't slide from one card to another.
- `_ChildDialog` is a `StatefulWidget` **so that it owns its
  `TextEditingController`** and releases it in `dispose()`. Releasing it right
  after `showDialog` would cause an error, because the dialog still uses it
  during its closing animation.

**Parent mode.** Changing a bank (− and +), resetting it to zero, deleting a
child and leaving the family need the parent code. Locked, a card shows a
single 🔒 button instead of − and +; the reset, delete and *Leave this family*
items show a lock. Typing the code unlocks
parent mode for 2 minutes (`ParentLock`, [§4.4](#44-parent-mode--libparentdart)).
Adding a child and changing their name or animal stay open: a new child starts
with an empty bank.

`HomeScreen` does not depend on Firebase: it receives the store, the family code
and a "leave" function. The widget test builds it with an in-memory store.

### 4.2 `TimerScreen` — `lib/timer_screen.dart`

It is a `StatefulWidget`, and the heart of the app. It listens to the store,
because another device can change the child's bank while it is open; in the
*choose* phase, the amount offered never exceeds what is left.

#### State machine

```
            Start (withdraw N)            Pause
   ┌────────┐ ───────────▶ ┌─────────┐ ─────────▶ ┌────────┐ ── Stop ──▶ home screen
   │ choose │              │ running │            │ paused │             (child mode: choose)
   └────────┘              └─────────┘ ◀───────── └────────┘
       │                     ▲    │       Resume       🔒 held
     Back                    │    │ remaining = 0
       ▼          +1/+5/+10  │    ▼
  home screen     or All     │  ┌──────────┐
                             └──│ finished │ ── Stop ──▶ home screen (child mode: choose)
                                └──────────┘
                                   🔒 held        (Parent + code: leave from 🔒)
```

- **choose**: the child picks how much to withdraw, between one minute (or the
  whole bank if less is left) and the whole bank. Shortcuts 5 / 10 / 15 / 30 min
  and *All*, plus − and + buttons (one minute per step, held down to repeat).
  The default proposal is 10 minutes, or the whole bank if it holds less. This
  is the only phase with a back arrow.
- **running**: only a *Pause* button. No back arrow, and the system back button
  does nothing: leaving a countdown always goes through *Pause* then *Stop*.
  The child may of course switch to another app (that is the point): the
  countdown goes on, shown in the status bar.
- **paused** 🔒: *Resume*, or *Stop*. The child is **held** on this
  screen (see below) until one of them, or until a parent leaves with the code.
- **finished** 🔒: the app has been brought to the foreground by the alarm, and
  **the child must choose**:
  - *+1 min*, *+5 min*, *+10 min* (only those the bank can afford) or *All (…)*:
    starts a new countdown. If the alarm brought the app forward, the app is
    then **sent back**, revealing the app the child was using;
  - *Stop*: the countdown is over; the app returns to its home screen, or in
    child mode to the *choose* screen, where the child is held again;
  - a discreet *Parent* button lets a parent leave with the code.

  With an empty bank, no more time is offered: "The bank is empty. Ask a parent
  for more time!". In child mode the child then stays on their choose screen,
  held, until a parent adds minutes. (Version 1.0 also put the tablet to sleep
  through a device administrator right; it was removed: holding the child in
  the app is what matters, and Google Play frowns on device administrators.)

**Held** (🔒, `_hold()` / `_release()`): no back arrow, the system back button
does nothing, and leaving the app (Home, Recents) shows a full-screen window
over the other apps (`Guard.kt`) whose only button brings Pitchoune Timer back.

#### Measuring time: an absolute end time

The screen does **not** decrement a counter on every tick. On start, it computes
`_end = now + remaining`. On every tick (every 100 ms), it recomputes
`remaining = _end − now`.

Benefits:
- no drift, even if ticks are lost (busy phone, app in the background, frozen
  process);
- when the app comes back to the foreground, a single computation is enough to
  correct the display.

It is the same idea as a *deadline* computed with `CLOCK_MONOTONIC` rather than a
`sleep(1)` counter in C. One nuance: `DateTime.now()` is a wall clock, so
manually changing the phone's time would distort the countdown.

#### Spending the bank

| When | Action |
|---|---|
| Start of a countdown (`_withdraw`) | Records `balanceAtStart` and `total`; nothing is debited yet. Marks the child as running on this device (`markRunning`) and shows the countdown in the status bar |
| Every 5 s during the countdown | `_save()`: debits the time spent since the last save (`debit(spent − debited)`) |
| Pause | `_save()` + cancel the alarm, the session, the running mark and the status bar countdown; the child is held |
| App goes to the background (`didChangeAppLifecycleState`) | `_save()` |
| Leaving the screen (`PopScope`) | `_save()` + cancel the alarm, the session and the running mark |
| End (`_finish`) | Debits what is left of `total`, session and running mark deleted, **alarm kept** (it is what brings the app back if the countdown ended in the background) |

#### Keeping the screen awake

While the phase is `running`, `Screen.keepOn(true)` stops the phone from going
to sleep, so the child can watch the countdown. It is switched off on pause, at
the end, and when the screen is closed (`dispose`). See
[§7.2](#72-screen-control). It is a window flag rather than a wake lock: Android
only honours it while the app is visible, so a forgotten flag cannot drain the
battery behind another app.

Stopping early (*Pause* then *Stop*) leaves the unused part of the withdrawal in
the bank: only the time actually spent is debited, **rounded down to the
minute**. `_leave()` gives back the seconds of the last minute started
(`refund(debited % 60)`), so the bank always stays in whole minutes, rounded in
the child's favour. The refund is an increment computed from this screen's own
counter, never from a value read back from Firestore, which could be stale. If the process is killed
abruptly, at most 5 seconds are lost.

#### Rendering

| Sub-component | Role |
|---|---|
| `_Gauge` (`CustomPainter`) | White disc, track, 12 ticks, arc with a gradient, "pearl" at its tip. In *choose*, the arc shows the share of the bank being withdrawn; while counting, the share of the withdrawal left |
| `_gaugeCenter()` | Bouncing avatar, name, `mm:ss` time in tabular figures |
| `_bounce` (`AnimationController`) | Makes the avatar bounce during the countdown |
| `_pulse` (`AnimationController`) | Makes the gauge beat during the last minute |
| `ConfettiBurst` | Confetti explosion at the end. If the countdown ended while the app was hidden (`_finishedUnseen`), it is fired again when the app comes back to the foreground (`_burst`) |

During the last minute, the gauge and the background turn orange (`kWarning`).

#### `timerRoute()`

A function that builds the opening transition (zoom with overshoot, plus fade).
It is shared by the home screen and by `main()`, which uses it to resume.

#### Child mode (`standalone`)

In child mode, `TimerScreen` is the root of the app rather than a screen
pushed over the home screen, and the child is **held in the app until they
start a countdown**:
- in the *choose* phase, the screen is held (🔒) like the paused and end
  screens: leaving the app shows the guard window ("Hi Emma! Go back to
  Pitchoune Timer and start your countdown."). The hold is released by *Start*,
  and comes back after every countdown;
- **unlocking the tablet always shows it**, on this child's choose screen, even
  if Android had closed the app: a native service (`ChildModeService`, with a
  discreet "child mode" notification) listens to unlocks and opens the app,
  unless a countdown is running. `_FamilyHome` starts it when child mode is on
  and stops it in parent mode (`Screen.setChildMode`); `BootReceiver` restarts
  it after a reboot;
- **Pitchoune Timer is the home screen of the child's account.** This is what
  brings it back after a restart: on the tablet used here, the child's account
  (a restricted profile) leaves the app *stopped* after a restart, and a
  stopped app receives nothing, not even `BOOT_COMPLETED` (§9.10). Android
  always starts the home app, though: at login, on the Home button, and when
  the child closes another app, they land on their timer;
- since the usual launcher is gone, while a countdown runs a **My apps** button
  next to *Pause* opens a sheet with the account's apps (`showAppsSheet` in
  `lib/apps.dart`); on a restricted profile these are exactly the apps the
  parent allowed. After the parent code (*Parent* button), an *Apps (parent)*
  button gives the same list;
- a discreet *Parent* button (code) lets an adult leave the app; the hold comes
  back as soon as the app returns to the front, or when a countdown starts;
- where it would close (after *Stop* or the parent exit), it goes back to the
  *choose* phase instead (`_leave()`), held again;
- there is no back arrow, and the system back button does nothing;
- in the *choose* phase, a ⚙ button opens the settings, behind the parent code;
- the permission requests, normally made by the home screen, are made when the
  child presses *Start*;
- once a parent refills an empty bank (from another device), an amount is
  proposed again automatically.

### 4.3 `FamilyScreen` — `lib/family_screen.dart`

Shown on a device that belongs to no family yet: *Create a family*, or join
one: **Scan the QR code** (main button) or type the code. Scanning opens a
camera screen (`scanFamilyCode` in `lib/family_qr.dart`: `MobileScanner`, QR
codes only, a frame to aim, a button for the other camera); the first valid
family code found closes it, fills the field and joins at once. A QR code that
is not a family code shows a hint instead. The camera permission is asked by
`mobile_scanner` the first time; refused, the code can still be typed. Network actions show a spinner and a readable error
("No family has this code", "Check the internet connection"). If the very first
anonymous sign-in failed (no network), only a *Try again* button is shown.

### 4.4 Parent mode — `lib/parent.dart`

| Element | Role |
|---|---|
| `kParentCode` | The code, `728` |
| `ParentLock` | `ChangeNotifier`. `tryUnlock(code)` opens parent mode for 2 minutes; a 1-second ticker refreshes the banner and locks again at the end. `ensure(context)` returns true at once if unlocked, otherwise shows the keypad |
| `_CodeDialog` | Big-key keypad, one dot per digit; checks automatically after the third digit, shakes off a wrong code |

One `ParentLock` per family, created in `main.dart` next to the store, and
shared by the home screen, the timer screen and the settings button.

**A UI lock, not a security barrier.** The code is checked in the app, and it
is written in the source code. It keeps a child from changing their own time;
it does not protect against someone who reads the code or opens the database.
Real protection would check the code on a server, for instance with a
Firestore rule. Accepted here: the threat is a curious child, not an attacker.
`ParentLock` stores an expiry time rather than a boolean, so `unlocked` is
computed (`now < until`) and can never stay open by mistake.

### 4.5 `SettingsScreen` — `lib/settings_screen.dart`

Reached with the ⚙ button, after the parent code: from the home screen in

- **Permissions and setup**: opens `SetupScreen` (§4.6). Switching to child

## 5. Visual effects and components — `lib/effects.dart`

These components are **reusable and independent from the model**: they don't
know about `Child`.

| Component | Technique | What it illustrates |
|---|---|---|
| `PitchouneTitle` | Looping `AnimationController` + one `Transform.translate` per letter, with an `i × 0.4` phase shift | A wave from a single controller and a `sin` function |
| `BubbleBackground` | `CustomPainter` tied to the animation (`super(repaint: anim)`) | Repainting **without rebuilding widgets**: very cheap |
| `ConfettiBurst` | 140 particles, ballistic path `p = p0 + v·t + ½·g·t²`, fade-out at the end | Simple physics computed on every frame |
| `RoundButton` | `GestureDetector`: tap + long press, with an accelerating repeat | The gesture arena (below) |
| `ChildAvatar` | Circular `Container` with a `RadialGradient` | — |

**The gesture arena.** When a finger touches the screen, **every** gesture
detector under it enters a competition: the − or + button's, but also the one
of the card that contains it. Only one wins. If the button only listened to
taps, the card's long-press detector would win after half a second, cancel the
button's repeat, and open the card's menu. That is why `RoundButton` declares
its own `onLongPressStart` / `onLongPressEnd`: the deepest detector registers
first in the arena, so the button wins the long press. *Qt analogy:* close to
`event->accept()`, except that the decision is collective and deferred.

**`BubbleBackground` detail:** each bubble has an **integer** speed (1 or 2
laps per cycle), so `(t × speed + phase) mod 1` loops with no visible jump when
the animation restarts from 0.

**`RepaintBoundary`** around the bubbles: the background is painted on its own
layer. Without it, every bubble frame would also force the cards on top of it to
be repainted.

## 7. Native Android code

Everything Flutter cannot do on its own goes through two **method channels**,
each wrapped in a Dart facade that does nothing outside Android.

| Channel | Dart facade | Kotlin | Methods |
|---|---|---|---|
| `pitchoune/alarm` | `Alarm` (`lib/alarm.dart`) | `MainActivity.kt` → `Alarm.kt` | `schedule`, `cancel`, `hasPermission`, `requestPermission` |
| `pitchoune/screen` | `Screen` (`lib/screen.dart`) | `MainActivity.kt` → `Guard.kt`, `CountdownNotification.kt`, `ChildModeService.kt`, `Apps.kt` | `keepScreenOn`, `moveToBack`, `setBlocked`, `suspendGuard`, `showCountdown`, `hideCountdown`, `canNotify`, `requestNotify`, `appVersion`, `isBatteryUnrestricted`, `openAppSettings`, `setChildMode`, `isHome`, `openHomeSettings`, `listApps`, `launchApp` |

### 7.1 The end-of-countdown alarm

When the countdown reaches 0, the app must come to the front **even if the child
is in another app or the screen is locked**. Dart code alone cannot do it:

- In the background, Android **freezes** and then **kills** processes, so the
  Dart `Timer` stops running.
- Since Android 10, an app in the background is **not allowed** to start an
  activity. There are a few exceptions, including the "Display over other apps"
  permission (`SYSTEM_ALERT_WINDOW`).

```
 Dart (TimerScreen)            Kotlin                          Android system
 ──────────────────            ──────                          ──────────────
 _run()
   Alarm.schedule(end)  ═════▶ MainActivity (MethodChannel)
                                 Alarm.schedule() ───────────▶ AlarmManager
                                                               .setExactAndAllowWhileIdle
        … the child switches app, the screen locks …
                                                               end time reached
                               AlarmReceiver.onReceive() ◀──── broadcast
                                 ├─ plays the notification sound
                                 └─ startActivity(MainActivity, extra=alarm)
                               MainActivity.onNewIntent()
                                 └─ setShowWhenLocked / setTurnScreenOn
 didChangeAppLifecycleState(resumed)
   ├─ process alive  : _tick() ▶ _finish() ▶ confetti
   └─ process killed : main() ▶ session found ▶ TimerScreen(resume) ▶ confetti
```

`Alarm.kt` holds a single alarm, the **end** alarm (request code 4242),
handled by `AlarmReceiver`.

**Why an intermediate `BroadcastReceiver`** rather than a `PendingIntent` that
opens the activity directly? Since Android 14 and 15, the rules around starting
an activity through a `PendingIntent` have tightened. With a receiver, **our own
process** calls `startActivity`, and it directly benefits from the exception
granted by the "Display over other apps" permission.

### 7.2 Screen control

| Feature | Kotlin | How |
|---|---|---|
| Screen kept awake while a countdown is visible | `MainActivity` | Window flag `FLAG_KEEP_SCREEN_ON` (honoured only while the window is visible) |
| Back to the previous app after *+N min* | `MainActivity` | `moveTaskToBack(true)` |
| Child held (paused, end, and in child mode the choose screen) | `Guard.kt` | While `Guard.active`, `MainActivity.onStop` adds a full-screen `TYPE_APPLICATION_OVERLAY` window over every other app; `onStart` removes it. If the hold starts while another app is in front, the window is shown at once. Its title and message are given by the Dart code for each situation |
| Child mode: app opened at every unlock | `ChildModeService.kt` | A *foreground service* (type `specialUse`, low-importance permanent notification) registers in code a receiver for `ACTION_SCREEN_ON` and `ACTION_USER_PRESENT`. When the screen turns on, and again once unlocked, unless a countdown is running (`CountdownNotification.isRunning`), it starts `MainActivity` with `NEW_TASK \| REORDER_TO_FRONT`, normally allowed thanks to "Display over other apps". 1.5 s after the unlock, if the app is still not on screen (`MainActivity.visible`), Android has refused: the guard window is shown instead (`Guard.invite`), whose button opens the app (a tap on our own window is always allowed to). `START_STICKY`: Android restarts it if it kills it. Started by the Dart side (`setChildMode`), by `MainActivity.onCreate` and by `BootReceiver` |
| Child mode after a restart | `BootReceiver.kt` | On `BOOT_COMPLETED` (sent after the first unlock, sometimes many seconds later) and `MY_PACKAGE_REPLACED` (app updated), reads the mode written by the Dart side (`FlutterSharedPreferences`, key `flutter.pitchoune.mode`) and starts `ChildModeService` asking it to open the app at once (the unlock is already past). The opening is done by the service, not the receiver: a receiver's process may be frozen as soon as `onReceive` returns, which would cancel the 1.5 s check and its invitation window. If the service is refused, the receiver opens the app itself and stays alive 3 s with `goAsync()` |
| Over the lock screen when the alarm rings | `MainActivity` | `setShowWhenLocked` / `setTurnScreenOn`, only for an activity launched by the alarm |

### 7.3 Countdown in the status bar — `CountdownNotification.kt`

An app cannot write text in the status bar. What it can do is post a
notification, whose **small icon** is shown there. So while a countdown runs:

- the small icon is **drawn on the fly** (`Icon.createWithBitmap`, 96 × 96
  pixels): a small stopwatch and the unit on the top line, the number in big
  below. More than one minute left: whole minutes rounded up ("12 mn"). In the
  last minute: every second ("60 s", "59 s"…). Android limits an app to a few
  notification updates per second, so one per second is fine. Android keeps only
  the alpha channel of status bar icons and tints them itself, so everything is
  drawn opaque on a transparent background;
- a **refresh alarm** (`CountdownRefreshReceiver`, request code 4244) re-posts
  the notification at each minute change. It works even when the Dart code is
  frozen in the background: the end time and the name are kept natively, in a
  dedicated SharedPreferences file;
- alarms cannot do the **last minute**: Android never fires an app's alarm less
  than about 5 seconds after it was set (the icon then moved by steps of 5 s).
  So at the start of the last minute, `CountdownTicker` takes over: a short
  *foreground service* (type `shortService`, at most 3 minutes, no special
  permission) whose foreground notification *is* the countdown notification.
  Being in the foreground keeps the process awake, so a plain `Handler` redraws
  the icon at each second change, and the service stops itself at the end (or
  when the countdown is paused or stopped). If Android refuses to start it,
  the refresh alarm is kept as a fallback;
- in the notification shade, the notification shows a live chronometer with the
  seconds (`setUsesChronometer` + `setChronometerCountDown`), updated by the
  system itself;
- it is *ongoing* (the child cannot swipe it away), and removed on pause, at
  the end, and automatically at the end time even if the app is dead
  (`setTimeoutAfter`).

On Android 16 devices that support *Live Updates*, the notification also asks
to be promoted to a chip next to the clock (`EXTRA_REQUEST_PROMOTED_ONGOING`,
permission `POST_PROMOTED_NOTIFICATIONS`). Manufacturers decide whether they
support it: on the Samsung tablet used here, only the icon is shown, hence the
minutes drawn into the icon.

Since Android 13, posting notifications needs a runtime permission
(`POST_NOTIFICATIONS`), requested like the others.

### 7.4 Permissions summary

| Permission | Kind | Used for | Asked |
|---|---|---|---|
| `SYSTEM_ALERT_WINDOW` "Display over other apps" | Special (settings screen) | Coming to the front at the end; guard window | Setup screen |
| `POST_NOTIFICATIONS` | Runtime (system prompt) | Countdown in the status bar | Setup screen |
| Battery "Unrestricted" (not a manifest permission) | A choice on the app's system page | Alarms and child mode not stopped in the background | Setup screen |
| `CAMERA` | Runtime (system prompt) | Scanning the family QR code | The first time *Scan the QR code* is used |
| `USE_EXACT_ALARM` (13+), `SCHEDULE_EXACT_ALARM` (≤ 12) | Normal / granted at install | Alarm on time, even in Doze | Never |
| `RECEIVE_BOOT_COMPLETED` | Normal | Child mode: reopen the app after a restart | Never |
| `FOREGROUND_SERVICE`, `FOREGROUND_SERVICE_SPECIAL_USE` | Normal | Child mode: the service that listens to unlocks | Never |
| `POST_PROMOTED_NOTIFICATIONS` | Normal | Live Update chip | Never |

The setup screen (§4.6) groups every request, at the first launch (and at the
next ones while something is missing).

**Battery.** `REQUEST_IGNORE_BATTERY_OPTIMIZATIONS` would let the app ask
directly for the exemption, in a system dialog. Google Play only accepts it
for some kinds of apps, so the setup screen opens the app's system page
instead, where the parent chooses Battery → Unrestricted; the app only checks
the result (`isIgnoringBatteryOptimizations`).

**`USE_EXACT_ALARM`** is granted automatically, but Google Play reserves it for
alarm-clock or timer apps. For a Play Store release, it would have to be
justified, or replaced by `SCHEDULE_EXACT_ALARM`, which the user must grant in
the settings.

### 7.5 Troubleshooting

The native code logs under the `Pitchoune` tag, and the Dart code prefixes its
messages with `Alarm.`. Start a one-minute countdown, then check the chain link
by link:

```bash
# 1. Traces: channel registration, scheduling, reception, foreground
adb logcat -s Pitchoune:* flutter:*

# 2. Is the alarm registered by the system?
adb shell dumpsys alarm | grep -i -B2 -A6 pitchoune

# 3. Are the permissions granted?
adb shell appops get fr.pitchoune.timer SYSTEM_ALERT_WINDOW
adb shell dumpsys package fr.pitchoune.timer | grep -i alarm
```

| Symptom in the traces | Broken link |
|---|---|
| No `Channels pitchoune/alarm and pitchoune/screen registered` at startup | The provided `MainActivity.kt` is not the one being compiled (wrong package or wrong folder) |
| `Alarm.schedule: MissingPluginException` | Same cause |
| `EXACT alarm scheduled…` then nothing at the end time | The `<receiver>` is missing from the manifest, or its name doesn't match the Kotlin class (`.AlarmReceiver`) |
| `INEXACT alarm…` | Exact alarm permission denied: Android may delay the alarm by several minutes |
| `Alarm received…` but no sound | Notification volume at zero, or Do Not Disturb mode |
| `Guard: "Display over other apps" not granted` | Leaving the end screen is not prevented: grant the permission |
| `Countdown notification: permission not granted` | Notifications not allowed: no countdown in the status bar |
| A notification but no chip next to the clock | Android older than 16, Live Updates turned off for the app, or a manufacturer restriction |
| "Pitchoune Timer could not start" on screen | A startup step failed or timed out; the message is the exception. `adb logcat -d \| grep -E "flutter\|Startup"` gives the details (Dart messages use the `flutter` tag) |
| `Cannot show the app` | "Display over other apps" not granted. Some vendor skins (Xiaomi, Oppo…) also have their own setting, such as "Display pop-up windows while running in the background" |

`fr.pitchoune.timer` is the *application id* (`applicationId` in
`android/app/build.gradle.kts`). The Kotlin code keeps the package `flutter
create` generated, `com.example.pitchoune_timer` (`namespace`), hence component
names such as `fr.pitchoune.timer/com.example.pitchoune_timer.HomeActivity`.

## 8. Learning notes: Dart / Flutter for a C, C++ and Python developer

*The analogies are landmarks, not exact equivalences.*

### 8.1 Dart at a glance

| Dart | C++ | Python | Note |
|---|---|---|---|
| `int`, `double`, `String`, `bool` | `int64_t`, `double`, `std::string` | `int`, `float`, `str` | `int` is 64 bits natively. Everything is an object, even `int` |
| `var x = 3;` | `auto x = 3;` | `x = 3` | **Static** typing, inferred |
| `final x = f();` | `const auto x = f();` (at runtime) | — | Assigned only once |
| `const x = 3;` | `constexpr` | — | Evaluated at compile time and **canonicalised**: two identical `const Color(0xFF…)` are the same object |
| `String?` | `std::optional<std::string>` | `Optional[str]` | **Null safety**: a type without `?` can't be `null`, checked at compile time |
| `x!` | `*opt` (unchecked) | — | "I guarantee it isn't null": throws otherwise |
| `x ?? y` | `opt.value_or(y)` | `x if x is not None else y` | |
| `late final T x;` | — | `@cached_property` | Initialised later, or on first read |
| `(String, String)` and `r.$1` | `std::pair` / `std::tuple` | `tuple` | **Records** (Dart 3): return several values without a class |
| `switch` expression with `when` | — | `match … case … if` | Pattern matching, exhaustive over an `enum` |
| `'Hello $name, ${a + b}'` | `std::format` | f-string | |
| `[for (x in l) f(x), if (c) y, ...other]` | — | list comprehension | Directly inside a list literal |
| `obj..a = 1..b = 2` | — | — | **Cascade**: chain calls on the same object |
| `f({required int a, int b = 0})` | — | `def f(*, a, b=0)` | **Named** parameters, everywhere in Flutter |
| `f([int b = 0])` | `f(int b = 0)` | `def f(b=0)` | Optional positional parameters |
| `_name` | `private` | `_name` (convention) | **Private to the file (library)**, not to the class! Two classes in the same file see each other's private members |
| `class A with M` | multiple inheritance (limited) | Python mixin | **Mixin**: reuse code without a hierarchy (`TickerProviderStateMixin`) |
| `implements` | pure abstract class | `Protocol` / ABC | Every class is implicitly an interface |
| `factory Child.fromJson(...)` | static factory function | `@classmethod` | Constructor that may return an existing instance or a subclass |
| `Child.fromJson` | — | — | **Named constructor**: replaces overloading, which doesn't exist in Dart |

**No function overloading.** Named parameters or named constructors are used
instead.

**Generics are reified** (unlike Java): a `List<int>` knows its type at runtime.

### 8.2 Memory: garbage collection, hence `dispose()`

Dart has a **garbage collector**, like Python. There is no `delete`, no
destructor, and no **RAII**. As a result, anything that holds an **external or
active** resource must be released explicitly in `dispose()`:
`AnimationController`, `Timer`, `TextEditingController`, `StreamSubscription`,
observers (`WidgetsBinding.instance.removeObserver`).

Rule of thumb: **whatever you create in `initState` (or a `late final`), you
release in `dispose`**, like a constructor/destructor pair written by hand.

### 8.3 Compilation

- **Debug**: the Dart virtual machine with a **JIT**. This is what enables *hot
  reload*: modified code is injected into the running process, and screen state
  is kept.
- **Release** (`flutter build apk`): **AOT** compilation to native ARM machine
  code, with *tree shaking* (unused code is removed). There is no VM anymore.
- Consequence: performance measured in debug is **not representative**. Use
  `flutter run --profile` to measure.
- On Android, a release build also runs **R8** on the Java/Kotlin side by
  default: it shrinks and renames the JVM code, removing whatever it believes
  unused. Code reached only by *reflection* (by name, at run time) looks
  unused to it. Here it removed methods the plugins need, and the release
  build stopped at startup with a `NoSuchMethodError` that the debug build
  never showed. R8 is therefore turned off (`isMinifyEnabled = false` in
  `android/app/build.gradle.kts`); the alternative is a list of *keep rules*
  for every plugin. Lesson: **always test the release build** before
  distributing it.

### 8.4 Asynchrony: a single event queue

- Each Dart **isolate** is **single-threaded**, with an event loop, like
  Python's `asyncio` or Qt's event loop.
- `Future<T>` ≈ `asyncio.Future` / `QFuture`. `async`/`await` works as in Python.
- **No mutex needed** within an isolate: two pieces of Dart code never run at
  the same time. An `await` is the **only** point where other code can slip in.
  That is why `mounted` is checked again after an `await`.
- A `Future` that isn't awaited (`_save();` without `await`) is
  "fire and forget". It is intended for saving, but any error is then not
  reported to the caller.
- Real parallelism goes through **another isolate** (`Isolate.run`). Isolates
  share no memory and communicate by messages, much like Python
  `multiprocessing` processes.
- `Timer` ≈ `QTimer` (`Timer.periodic` ≈ a repeating `QTimer`).
- A `Stream<T>` is a sequence of values over time (`Future<T>` is a single one).
  You `listen` to it and get a `StreamSubscription`, to `cancel` when done.
  Firestore's `snapshots()` is a stream that never ends: it emits again after
  every change. *Analogies:* a Python async generator (`async for`), or a Qt
  signal emitted repeatedly.

### 8.5 The Flutter model

**Everything is a widget**, including layout (`Padding`, `Center`, `Row`…), and a
widget is an **immutable description** of the UI, not the UI itself.

Flutter maintains **three trees**:

| Tree | Role | Lifetime |
|---|---|---|
| Widgets | Immutable configuration, recreated on every `build()` | Very short (lightweight objects) |
| Elements | Instances: the link between a widget and its place in the tree; they hold the `State` | Long |
| RenderObjects | Layout and painting | Long |

`build()` is called **often** (on every `setState`, every animation frame…). It
must therefore be **fast and free of side effects**: no file writes, no network
calls, no `Timer` creation.

**`StatelessWidget` vs `StatefulWidget`.** The latter separates the immutable
configuration (the widget) from the mutable state (the `State` object), which
survives rebuilds. `State` lifecycle:
`initState` → `build` (×N) → `didUpdateWidget` (if the parent changes the
configuration) → `dispose`.

**Layout: one rule to remember.**
> *Constraints go down, sizes go up, the parent sets the position.*

A parent gives its child a minimum and maximum size, the child picks its size
within those bounds, and the parent decides where to place it. Most *overflow*
or *unbounded height* errors come from a widget receiving an infinite constraint
(for example a `Column` inside a `ListView`).

**`BuildContext`** is a widget's position in the tree. `Theme.of(context)` or
`Navigator.of(context)` **walk up** the tree to find the matching ancestor
(`InheritedWidget`), a bit like searching for a parent `QObject`.

**`Key`s** identify a widget among its siblings when the list changes
(insertion, deletion, reordering). Without a key, Flutter matches elements by
position, and the state of one item can end up attached to another.

### 8.6 Qt / QML equivalents

| Qt / QML | Flutter |
|---|---|
| QML `Item` | `Widget` |

### 8.8 Common pitfalls

1. **`setState()` after `dispose()`**: a `Timer` or `Future` completing after the
   screen is closed. Cancel it in `dispose()` or check `mounted`.
2. **`context` after `await`**: check `context.mounted`.
3. **Heavy work in `build()`**: move it to `initState` or to a cached `Future`.
4. **Forgetting `const`** before constant widgets: harmless, but `const` avoids
   needless rebuilds (the linter flags it).
5. **Believing `_` makes something private to the class**: the scope is the
   file.
6. **Comparing performance in debug.**
7. **Changing a native file** (manifest, Kotlin) and being surprised that *hot
   reload* doesn't apply it: stop the app and `flutter run` again.

## 9. Learning notes: the Android platform for an embedded developer

*Flutter draws the interface, but the app lives inside Android, whose rules
explain most of the native code of this project.*

### 9.1 An app is not a daemon

On an embedded Linux system, a service starts at boot and runs until it is
stopped. On Android, **the system owns the process**:

- An app's process is created on demand and can be **frozen** (no CPU at all)
  as soon as nothing of it is visible, then **killed** to recover memory, with
  no signal the app can rely on.
- What survives is what the app declared to the system: **alarms**
  (`AlarmManager`), **receivers** listed in the manifest, **notifications**,
  scheduled jobs, and *foreground services* (which show a permanent
  notification).

That is the reason for the design of this app: the countdown time is computed
from an absolute end time, the end is entrusted to a system alarm, and the
running countdown is saved (`TimerSession`) to be rebuilt after a kill.

### 9.2 Activities and their lifecycle

An **activity** is one screen of an app as Android sees it. A Flutter app
usually has a single one (`MainActivity`), inside which Flutter draws every
screen.

```
onCreate → onStart → onResume  ⇄  onPause → onStop → (onDestroy)
           visible   in front       partly    hidden
                     and touched    hidden
```

Flutter forwards these states to Dart as `AppLifecycleState` (`resumed`,
`inactive`, `hidden`, `paused`), which `TimerScreen` listens to. `Guard.kt`
hooks `onStart` / `onStop` to know whether the app is visible.

### 9.3 Tasks and the back stack

Activities are grouped into **tasks**, which are stacked like windows. The
*Recents* screen shows the tasks. Bringing the app forward (`REORDER_TO_FRONT`)
or sending it back (`moveTaskToBack`) moves a whole task, which is how the app
returns the child to the game they were playing.

### 9.4 Intents, PendingIntents and broadcasts

- An **Intent** is a message: "open this screen", "this event happened".
  *Analogy:* a message on D-Bus or a local socket, routed by the system.
- A **PendingIntent** is an Intent handed to the system to be sent **later, on
  the app's behalf** (by an alarm, by a tap on a notification). It works even if
  the app's process is dead in the meantime.
- A **broadcast** is an Intent sent to whoever listens, received by a
  **BroadcastReceiver**. Receivers declared in the manifest can wake the app
  (`AlarmReceiver`). Since Android 8, most *implicit* system broadcasts can only
  be received while the app is running (registered in code).

### 9.5 Alarms and battery saving

`AlarmManager` is the system's timer service. To save battery, Android batches
and delays alarms, especially in **Doze** mode (screen off, device still).
`setExactAndAllowWhileIdle` asks for an exact alarm even in Doze, which needs
the exact-alarm permission. *Analogy:* a hardware RTC alarm that can wake the
system, as opposed to a software timer that only runs while the CPU does.

### 9.6 Kinds of permissions

| Kind | Granted | Examples here |
|---|---|---|
| Normal | Automatically at install | `USE_EXACT_ALARM`, `POST_PROMOTED_NOTIFICATIONS` |
| Runtime ("dangerous") | System prompt while the app runs | `POST_NOTIFICATIONS` |
| Special | A dedicated settings screen | "Display over other apps" |
| Device administrator | An activation screen, listing the policies | Not used (version 1.0 locked the screen with it) |
| Device owner | Only on a freshly reset device, with `adb` or an enterprise tool | Not used: true kiosk mode |

The rule of thumb: the more an app can affect the rest of the device, the more
explicit and visible the user's consent must be.

### 9.7 Windows: activities and overlays

Each activity draws in a **window**. An app holding "Display over other apps"
may also add free-standing windows of type `TYPE_APPLICATION_OVERLAY`, which
stay on top of every other app (but below the lock screen and the system bars).
`Guard.kt` uses one; chat "bubbles" and screen filters work the same way.
Flutter is not involved: the view is built with plain Android widgets.

### 9.8 Notifications and channels

Since Android 8, every notification belongs to a **channel** (here
"Countdown"), whose importance, sound and vibration the user controls in the
settings. An app cannot draw in the status bar: it posts notifications, and the
system decides how to show them (icon, shade, lock screen, and since Android 16
the Live Update chip).

### 9.9 Where an app's local data lives

*Question: are an app's local settings tied to the tablet's account?*

- `SharedPreferences` (and every file of the app) live in the app's private
  folder, `/data/user/<user number>/fr.pitchoune.timer/`. They belong
  to the **Android user profile** of the tablet (owner, child profile…), not to
  the Google account. Two profiles on the same tablet each have their own copy.
- They are deleted when the app is **uninstalled** or when its data is cleared
  (*Settings → Apps → Storage → Clear data*).
- Exception: unless the app opts out (`android:allowBackup`), Android's **Auto
  Backup** copies them to the Google Drive of the device's Google account, and
  restores them when the app is reinstalled or moved to a new device. This is
  the only link with the Google account.
- For Pitchoune Timer, what matters is shared in Firestore (children, banks).
  Locally there is only the family code, the running countdown, the anonymous
  Firebase identity, and the tablet account's mode (`DeviceSettings`). This
  per-profile storage is exactly what makes "child mode" work: on a shared
  tablet, the child's Android account and the parent's each keep their own
  mode. After a reinstall without a backup, the device gets a new
  identity and must type the family code again.

**One app, several users: one instance per user.** On a tablet with several
users, an app is installed once (one APK), but each user gets their own copy
of its data (above) and their own **process**: Android gives the app a
different Linux user id for each Android user (`uid = user number × 100000 +
app id`). So there are as many independent Pitchoune Timers as users who
opened it: each with its own mode, family code, countdown, alarms, permissions
("Display over other apps", notifications and battery exemption are granted
per user) and child mode service. Only the user on screen sees their windows;
the other users' processes may keep running in the background (their alarms
and Firestore listeners keep working) until Android stops them to save memory.
`BOOT_COMPLETED` is likewise sent to each user, when that user logs in for the
first time after the restart, not when the tablet starts.

### 9.10 Starting automatically

*Question: can an app start by itself as soon as the device is unlocked?*

Not directly, but there are four ways, from the lightest to the strongest:

| Approach | How | Limits |
|---|---|---|
| Unlock event | Listen to `ACTION_USER_PRESENT` and bring the app forward | Since Android 8 it can only be received by a **running** app: it needs a *foreground service* (permanent notification), started at boot with `BOOT_COMPLETED`. Starting the activity needs "Display over other apps". Battery savers (especially on Samsung) may kill the service |
| Home app | Declare the app as a **launcher** (`HOME` category) and make it the default | It then shows after every unlock and every Home press. The app must offer a way to open the other apps (it becomes the tablet's home screen) |
| Screen pinning | `startLockTask()` without being device owner | Android asks for confirmation each time, and anyone can unpin |
| Kiosk mode | App set as **device owner** + `startLockTask()` | True lock-in, but only possible on a factory-reset device, set up with `adb` |

**What Pitchoune Timer does in child mode** combines three things:
- the app **never leaves the front** while no countdown runs: the guard window
  sends the child back whenever they try;
- the *unlock event* approach, for when Android closed the app anyway (memory,
  battery saver, app never opened since the install): `ChildModeService`
  listens to `ACTION_USER_PRESENT` and opens the app. A `BOOT_COMPLETED`
  receiver (allowed in the manifest, unlike the unlock event) restarts it after
  a reboot or an update;
- the *home app* approach, for restarts on a restricted profile, where the app
  is left *stopped* and receives nothing (detailed below).

Why a *foreground* service: a plain background service is stopped by Android
after about a minute. A foreground service must show a notification, which is
the price to stay alive; its channel is set to low importance so it stays
quiet in the notification shade. Since Android 14 each foreground service
declares a type; none of the predefined ones (media, location…) fits, hence
`specialUse` with a sentence explaining the use (`PROPERTY_SPECIAL_USE_FGS_SUBTYPE`).

On Samsung, set the app's battery usage to **Unrestricted** (Settings → Apps →
Pitchoune Timer → Battery), otherwise the battery saver may still stop the
service. And an app freshly installed is in the *stopped* state: it receives
nothing (not even `BOOT_COMPLETED`) until it has been opened once by hand.

**And the Home app approach, for restarts.** On the tablet used here, the
logs showed that after a restart the child's account (a *restricted profile*)
leaves Pitchoune Timer in the **stopped** state: Android sends it nothing until
someone opens it by hand. `BOOT_COMPLETED` for that account was only delivered
to the app once the child had tapped its icon (since Android 15, a stopped app
receives it at that moment). No code can wake up a stopped app; the only
exception is the home app, which Android starts itself. So in child mode,
Pitchoune Timer is also the account's home screen:
- `HomeActivity` declares the `HOME` category. It is a translucent
  *trampoline*: each time it comes to the front, it forwards to `MainActivity`
  (with a 1-second safety net against loops). Keeping the home separate from
  `MainActivity` avoids having two copies of the Flutter screen, one in the
  home task and one in a normal task;
- it is **disabled** in the manifest (`android:enabled="false"`) and enabled
  only in child mode (`PackageManager.setComponentEnabledSetting`, kept per
  Android user). In parent mode it does not exist, so the account keeps its
  usual launcher;
- choosing it as the default home is up to the user (an app cannot do it
  itself): the settings screen opens `Settings.ACTION_HOME_SETTINGS`. If the
  restricted profile hides that screen, it can be done with adb (the user
  number is in `adb shell pm list users`):
  `adb shell cmd package set-home-activity --user 14 fr.pitchoune.timer/com.example.pitchoune_timer.HomeActivity`;
- the child's apps are listed by `Apps.kt` (`queryIntentActivities` on
  `MAIN`/`LAUNCHER`, which needs a `<queries>` entry in the manifest since
  Android 11's package visibility rules), with icons sent to Dart as PNG bytes.

### 9.11 Everyday Android tools

| Command | Role |
|---|---|
| `adb logcat -s Pitchoune:* flutter:*` | This app's logs (native and Dart) |
| `adb shell dumpsys alarm` | Alarms registered in the system |
| `adb shell dumpsys notification` | Notifications posted, and their flags (promoted or not) |
| `adb shell appops get <package>` | Special permissions ("Display over other apps"…) |
| `adb shell dumpsys package <package>` | Declared and granted permissions |
| `adb shell am start -n <package>/.MainActivity` | Start the app from the command line |
| `adb shell pm clear <package>` | Clear the app's data, as after a reinstall |

### 9.12 Identity, signing and distribution

*Question: what makes two APKs "the same app"?*

- The **application id** (`applicationId`, here `fr.pitchoune.timer`). It is
  the app's identity on the device, in Firebase and on the Play Store. Two
  different ids are two different apps, side by side, each with its own data.
  The Kotlin *package* (`namespace`) is only a source-code matter and can
  differ.
- The **signing certificate.** Every APK is signed; Android installs an
  update only if it is signed with the **same key** as the installed version,
  otherwise it refuses (the user would have to uninstall, losing the data).
  `flutter run` signs with a debug key generated on each PC, so an APK built
  on another PC cannot update it. Releases are signed with a dedicated key
  (`keytool`, settings in `android/key.properties`, kept out of git and backed
  up): losing it means no more updates.
- The **version code** (the number after `+` in `pubspec.yaml`): an update
  must have a higher one. `tool/release.sh` adds one at every release.

Distribution without the Play Store goes through **Firebase App
Distribution**: the APK is uploaded with the Firebase CLI, testers grouped by
an alias receive an email, install through the *App Tester* app, and are
notified of new versions. Android asks them once to allow installing apps
from that source ("unknown sources"), and Play Protect may warn about an
unknown developer.

### 10.4 Releasing to family and friends

Testers install the app from Firebase App Distribution; their guide is
[`INSTALL.md`](INSTALL.md).

#### One-time setup

1. **Firebase app.** The application id is `fr.pitchoune.timer`
   (`android/app/build.gradle.kts`). Register it in Firebase and regenerate the
   configuration files, then commit them:

   ```bash
   flutterfire configure --project=pitchoune-timer --platforms=android \
       --android-package-name=fr.pitchoune.timer --yes
   ```

   Devices that run the old `com.example.pitchoune_timer` build see the new one
   as another app: uninstall the old one, then set the new one up again.

2. **Release key.** Updates are only accepted when signed with the same key,
   so create it once and **back it up** (a lost key means testers must
   uninstall and reinstall):

   ```bash
   keytool -genkey -v -keystore ~/pitchoune-release.jks -keyalg RSA \
       -keysize 2048 -validity 10000 -alias pitchoune
   ```

   Then create `android/key.properties` (ignored by git):

   ```properties
   storePassword=<password>
   keyPassword=<password>
   keyAlias=pitchoune
   storeFile=/home/<you>/pitchoune-release.jks
   ```

3. **Testers.** Firebase console → *Release & Monitor → App Distribution →
   Get started*. In *Testers & Groups*, create a group whose alias is
   `family` and add the testers' email addresses.

#### Every release

From `main`:

```bash
tool/release.sh "What changed, in a sentence for the testers"
tool/release.sh "What changed" 1.1.0     # also sets a new version name
```

The script:
1. checks the release key, the tools, that everything is committed, and asks
   for confirmation if the branch is not `main`;
2. adds one to the build number (`version: name+build` in `pubspec.yaml`);
3. runs the tests, builds the APK and checks it is signed with the release
   key (`tool/build.sh`);
4. uploads it to App Distribution for the `family` group
   (`PITCHOUNE_TESTERS=<alias>` for another group);
5. commits `pubspec.yaml` and tags `v<name>+<build>`, then **asks** before
   pushing the branch and the tag to GitHub.

If it stops before the upload, `pubspec.yaml` is put back as it was.
